E2 – Price data over a web API: all options

MarketLens · decision overview for E2 (and the loading part of E6) · as of 13 Nov 2026

E2 is blocked on a few decisions that are yours to make. This page lists every option I see, with pros and cons, and marks my recommendation. Requirements that rule options in or out come from PROJEKT.md and AGENTS.md:

  • The default build (cmake -B build && cmake --build build && ctest --test-dir build) must work offline and without extra libraries.
  • Real HTTPS access is a CMake option that is off by default. Tests use a fake IHttpClient with recorded responses.
  • HTTP server and JSON parsing use header-only libraries inside the repo.
  • The API key comes from an environment variable and is never stored in the repo. A missing key is reported before the first request.
  • Use providers according to their terms and free quotas.
  • No new external dependencies without asking (AGENTS.md).

1C++ standard

PROJEKT.md says "C++17 backend", while AGENTS.md and CMakeLists.txt say C++20. The existing code (E5 tests, E6) already uses C++20 features: std::chrono::sys_days, year/month/day, floor<days>.

C++20 recommended

  • Matches AGENTS.md, CMakeLists.txt and all existing code: no rework
  • Calendar dates in <chrono> (needed for E2 date parsing and E6)
  • All recommended libraries support it
  • PROJEKT.md has to be corrected (one word)
  • No std::expected (that is C++23)

C++17

  • Matches the current text of PROJEKT.md
  • Works with older compilers
  • Contradicts AGENTS.md and CMakeLists.txt
  • E5 tests, E6 and the test helpers must be rewritten (no sys_days, no calendar types)
  • Date handling with std::tm/mktime depends on the time zone (we already saw this in E1)

2JSON library

E2 parses the provider response and the catalog. The library must be header-only and live in the repo (e.g. third_party/). E2 has to tell apart "invalid JSON" and "missing field".

nlohmann/json recommended

MIT · one header json.hpp · C++11 and later
  • Most widely used. Its API reads like normal C++ (j["close"].get<double>()), which makes it easy to explain in the exam
  • Its typed exceptions map directly onto the E2 error cases: parse_error → invalid JSON, out_of_range → missing field, type_error → wrong type
  • One file, very good documentation
  • Can also write JSON, which E8 needs for the server responses
  • Large header (~25k lines), so compiling is slower
  • Slower and more memory-hungry than RapidJSON/simdjson. That doesn't matter for a few KB of daily prices

RapidJSON

MIT · header-only · C++03 and later
  • Very fast, small memory footprint
  • Header-only, mature
  • Verbose API (HasMember, IsDouble, GetDouble for every field)
  • Error codes instead of exceptions: you have to translate them yourself
  • Development has been slow for years

simdjson

Apache-2.0 / MIT · amalgamated simdjson.h + simdjson.cpp
  • Fastest JSON parser available
  • Good error reporting
  • Not header-only: needs a .cpp file. That doesn't match the PROJEKT.md wording
  • Read-only: it can't write JSON, so E8 would need a second library
  • The on-demand API has pitfalls (values can only be read once, in order)

Boost.JSON doesn't fit

BSL-1.0 · part of Boost
  • Good quality, fast, can read and write
  • Needs Boost, a large external dependency
  • Header-only only in a special mode. Not "one file in the repo"

Glaze

MIT · header-only
  • Very fast, maps JSON directly onto structs
  • Newer versions need C++23, older ones may lack fixes
  • Heavy template code: compile errors are hard to read and the code is hard to explain
  • Many files, not a single header

Own parser

  • No dependency at all
  • Good for showing algorithmic skills
  • A lot of work: escapes, Unicode, numbers, nesting, error positions
  • High risk of bugs, and every bug needs its own test
  • Takes time away from the actual features (E7–E10)
  • The project description already says a library is used

3HTTPS client for live mode

Only active when the CMake option (e.g. -DMARKETLENS_LIVE_HTTP=ON) is set. The default build doesn't compile it. It implements IHttpClient, and the rest of the code doesn't know which library is behind it. All providers require HTTPS, so TLS support is mandatory.

cpp-httplib + OpenSSL recommended

MIT · one header httplib.h · HTTPS via CPPHTTPLIB_OPENSSL_SUPPORT
  • Same library as the E8 HTTP server: one dependency for client and server
  • Simple API: cli.Get(path) returns status and body. Timeouts can be set
  • Header-only, lives in the repo
  • HTTPS needs OpenSSL (libssl-dev) in the container. That's only for the live option, but it's a change to the Containerfile
  • Fewer features than curl (proxies, HTTP/2)

libcurl

curl licence (MIT-like) · system library · find_package(CURL)
  • The industry standard: very robust, every TLS and proxy case solved
  • Precise error codes (timeout, DNS, TLS) that map well onto E2 error cases
  • CMake has built-in support
  • C API: needs an RAII wrapper class (callback for the body, curl_easy_cleanup)
  • A second network library next to the server library
  • Needs libcurl-dev in the container (live option only)

Boost.Beast / Asio

  • Very powerful, asynchronous
  • Needs Boost plus OpenSSL
  • A lot of code for a simple GET. Hard to explain
  • Far more than this project needs

cpr

C++ wrapper around libcurl
  • Pleasant C++ API (cpr::Get(cpr::Url{...}))
  • Needs libcurl anyway, plus cpr itself (usually via FetchContent, which downloads during the build)
  • Two dependencies instead of one

curl command via popen not advisable

  • No library at all. Only the curl program is needed
  • Security risk: shell injection if a symbol or the key ends up in the command line, and the key is visible in the process list
  • Poor error handling (exit codes, stderr parsing)
  • Not portable, hard to test, looks like a hack in the exam

4Price data provider

Must deliver daily OHLCV data as JSON for many countries, with an API key (the DoD requires "missing key is reported"). Only official APIs with acceptable terms qualify. Free quotas change often: check the numbers below on the provider's pricing page before you decide.

Alpha Vantage recommended

  • Global stocks on the free tier via exchange suffixes. That fits "all countries" well
  • Simple JSON (TIME_SERIES_DAILY), well documented, widely used
  • Clear error signals inside the JSON ("Error Message", "Note"/"Information" when the quota is exhausted). Good test cases for E2
  • Only ~25 requests/day: the E7 disk cache is essential, and you must develop against fixtures
  • The quota error comes as HTTP 200 with a message in the body, not as 429. The code must detect it from the content
  • Index coverage on the free tier is limited

Twelve Data

  • Much larger quota (800/day)
  • Clean JSON with explicit code/status fields, and real 429 behaviour
  • Many international exchanges aren't in the free plan, which weakens "all countries"
  • Per-minute limit (8/min) needs throttling

EODHD

  • Best global coverage (stocks, indices, many exchanges)
  • Simple end-of-day JSON
  • Very small free quota and limited history on the free tier (verify the current terms)
  • Less common, so fewer examples online

Financial Modeling Prep / Tiingo / Finnhub

  • Generous quotas, good JSON
  • Fine for US securities
  • Free tiers mostly US-only for historical daily data, which doesn't fit "all countries"

Stooq doesn't fit the DoD

  • No key, many countries and indices
  • CSV, not JSON. E2 says "JSON response"
  • No key, so "missing API key is reported" can't be implemented or tested
  • No official API documentation or guaranteed terms

Yahoo Finance (unofficial) excluded

  • Free, very good coverage
  • No official public API: using it conflicts with "according to the provider's terms"
  • Endpoints change or break without notice
  • No key, so the same DoD problem as Stooq
Design note: because everything goes through IPriceSource, you can start with one provider and add a second one later (e.g. Twelve Data for US, Alpha Vantage for the rest) without touching the analysis code. The catalog then stores the provider symbol for each security.

5Rate data provider (E6 loading part)

E6 needs rate decisions (bank, country, date, rate) for several central banks via IRateSource. There is no single free API that lists "decisions". You usually get a daily rate series and derive the decisions from the days the rate changes.

FRED (St. Louis Fed) recommended

free API key · JSON · e.g. DFEDTARU/DFEDTARL (Fed target range), ECBDFR (ECB deposit rate)
  • One key and one JSON format for several central banks
  • Official, stable, well documented
  • Has a key, so "missing key" works the same way as in E2
  • Gives the date the rate takes effect, which can be a day or more after the decision. The event study would then measure a slightly shifted day. Document this or correct it
  • Coverage for BoE and BoJ as daily policy-rate series needs checking. Some are only monthly
  • Decisions without a rate change ("hold") are invisible in a change-point series

Official central bank APIs

e.g. ECB Data Portal (SDMX, JSON, no key), Bank of England database (CSV)
  • Primary sources, most accurate dates
  • The ECB API needs no key and supports SDMX-JSON
  • A different format per bank: one IRateSource implementation each
  • SDMX-JSON is deeply nested and awkward to parse
  • The BoE delivers CSV, and the BoJ has no simple API
  • No key, so the "missing key" logic doesn't apply

Versioned JSON file in the repo

hand-maintained list of real decision dates
  • Exact decision dates, including "hold" decisions
  • Works offline, no quota
  • Not a web API, so on its own it doesn't meet the E6 DoD
  • Must be updated by hand
  • Good as a fallback or for tests, not as the only source

6Error handling design

E2 must distinguish: network error / timeout, HTTP status (401, 404), quota (429), invalid JSON, missing fields, missing API key. A faulty catalog entry must not stop the others.

Exception hierarchy recommended

base QuellenFehler → NetzwerkFehler, ZeitueberschreitungFehler, HttpFehler(status), KontingentFehler, ParseFehler, KonfigurationsFehler
  • Consistent with E1–E6, which all use std::invalid_argument
  • Each case can be tested with EXPECT_THROW(..., KontingentFehler)
  • E7 can catch exactly NetzwerkFehler/KontingentFehler to fall back to stale cache data
  • Classic OOP (inheritance), easy to explain
  • Per-entry catalog errors must be caught and collected in a loop (a try/catch per security)
  • Control flow is less visible than with return values

Result type

own Ergebnis<T> or std::variant<T, Fehler>
  • Errors are visible in the function signature
  • Natural for "evaluate all securities, collect errors"
  • std::expected is C++23 and not available in C++20, so you'd have to write it yourself
  • Mixes two styles in the project (E1–E6 use exceptions)
  • More code at every call site

Error codes (enum + message)

  • Simple, no exceptions
  • Easy to forget to check
  • Needs out-parameters or pairs, which isn't modern C++
  • Inconsistent with the rest of the code
Combination: exceptions inside the sources, plus a small result struct for the catalog evaluation ({ erfolgreiche Wertpapiere, Liste der Fehler pro Symbol }). That meets "a faulty security doesn't prevent the others".

7Catalog format

The catalog describes symbol, name, country, currency (and the provider symbol) for any number of securities. A new country is added by a new entry, without changing code.

JSON file recommended

katalog.json: [{"symbol":"SAP","name":"SAP SE","land":"Deutschland","waehrung":"EUR","anbieterSymbol":"SAP.DEX"}, …]
  • Same library as for the API responses: no extra parser
  • Can hold optional or extra fields later (provider symbol, central bank)
  • The same error categories apply (invalid JSON, missing field)
  • Less pleasant to edit by hand than CSV (quotes, commas)
  • No comments allowed in standard JSON

CSV file

  • Very easy to edit, also in Excel
  • Compact, one line per security
  • Needs its own parser (quotes, commas inside names like "Apple, Inc.")
  • Flat. Hard to extend with nested data

TOML / INI

  • Readable, comments allowed
  • Needs another library (a new dependency)

Hard-coded in C++ violates the DoD

  • No parsing
  • A new country would need a code change, which the DoD explicitly forbids

8Matching central banks to securities (affects E6)

Today E6 matches by country. The ECB covers about 20 countries, so a German stock ("Deutschland") never matches an ECB decision ("Eurozone").

By currency recommended

  • Solves the euro area: EUR → ECB, USD → Fed, GBP → BoE, JPY → BoJ, CHF → SNB
  • Every security already has a currency, so no new data is needed
  • Economically sensible: a central bank sets the rate for its currency
  • Changes the E6 wording in PROJEKT.md ("country" → "currency")
  • Small code change in E6 plus tests
  • Edge case: a security listed in a foreign currency (e.g. an ADR in USD) is matched to the Fed

By country (current)

  • Exactly as PROJEKT.md says, no change needed
  • Doesn't work for the euro area unless every country gets its own copy of each ECB decision

List of countries per central bank

e.g. ECB: ["Deutschland","Frankreich","Italien", …] in the catalog
  • Stays "by country", as in PROJEKT.md
  • Most precise and flexible
  • More data to maintain (about 20 euro countries)
  • More code and more catalog error cases

9Test data (fixtures)

All tests run offline with a fake IHttpClient that returns stored responses from tests/fixtures/.

Both: recorded + hand-written recommended

  • Recorded real responses prove the parser works on real data
  • Small hand-written files cover each error case exactly (missing field, wrong type, quota message)
  • Recording costs a few requests of the free quota, once
  • The API key must be removed from recorded files and URLs before committing

Only recorded responses

  • Realistic
  • Error cases are hard to provoke on purpose. Large files

Only hand-written JSON

  • Small, exact, no quota used
  • Risk that the real format differs from what you assumed
